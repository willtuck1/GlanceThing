# GlanceThing fork

Electron host (`src/main`, `src/preload`, `src/renderer`) that pushes data over a websocket to a React client (`client/`) running on a Car Thing: **Chrome 69, 800×480 landscape**. Tabs, default order: Weather, Calendar, To-do, Sports, Fantasy, Spotify (the user can hide and reorder them). Current release line: `v0.0.16-tabs.N` (see `package.json`; M8 is tabs.7, M9A is tabs.8, M9B is tabs.9, M9C is tabs.10).

## Where things are
- Host ws server: `src/main/lib/server.ts` routes `{type, action, data}` to `src/main/lib/handlers/*.ts` (`name`, `hasActions`, `actions`, `handle(ws, data)`).
- App modules (M9A): each app is a module with one id (`weather`, `calendar`, `todo`, `sports`, `fantasy`, `spotify`; Parts B/C add `json:<id>`/`mcp:<id>`). Host manifest `src/main/lib/modules/<id>/index.ts` (`ModuleManifest` in `modules/types.ts`: feed sources, handlers, `dependsOn`, settings panel; per-app handler in `modules/<id>/handler.ts`), listed in `modules/registry.ts`. Client module `client/src/modules/<id>/` (`index.tsx` exports `{id, label, render}`, plus the tab and `types.ts`), listed in `client/src/modules/registry.ts`. Both registries use the same ids in default tab order. JSON connectors (M9B) are runtime modules `json:<id>` built by `connectors/modules.ts` `connectorManifest(c)`; `modules/registry.ts` `allModules()` = static `modules` + connectors, read at call time. Handler lookup is `findHandler(name)` in `handlers/handlers.ts` (`json:` names come from `allModules()`, so added/deleted connectors take effect at once; no core handler may start with `json:` or `mcp:`). Don't name anything "apps" (`handlers/apps.ts` is desktop shortcuts).
- MCP connectors (M9C): recipes are committed JSON in `src/main/lib/connectors/recipes/<id>.json` (bundled with `import.meta.glob`, so a new file needs a desktop build but no client release), validated by `mcp/recipes.ts` `parseRecipe` (id = file name; exactly one of `tool:{name,args}`/`resource:{uri}`; layout + B mapping; ≤5 user `settings`); invalid files fail `mcp/recipes.test.ts`; args are literals, `{$host: now|today|dayStart|dayEnd, offsetDays?, format?}` (host system timezone) or `{$setting: key}`, resolved by `mcp/args.ts`. Only shipped recipe: `example-tasks` against the test-only server `mcp/testServer` (nothing listens on its default URL outside tests). Claude's own connector logins can't be reused; each MCP server is signed into once from desktop Settings. `Connector.source` is `JsonSource | McpSource` (`kind:'mcp'`, `recipeId`, `serverUrl`, `settings`; layout and mapping copied from the recipe), module id `mcp:<id>` (`connectorModuleId`, `isConnectorModuleId`, `CONNECTOR_PREFIXES` in `connectors/types.ts`). Feeds call `connectors/mcpHook.ts` `runMcpConnector` (runner set with `setMcpRunner`). Secure keys `mcpAuth.<id>.{tokens,client,verifier}` are protected and deleted with the connector; `store.ts` `bumpConnectorRevision(id)` rebuilds the feed and drops its cache. OAuth lives in `src/main/lib/mcp/auth/`: `signIn.ts` `signIn(id)` (saved connector only; SDK `auth()` via `safeFetch`, one-shot `loopback.ts` on 127.0.0.1 `/callback` (only a callback with the matching state is consumed; others get 400), authorize URL https or loopback http only, never rejects, fixed error strings) and `ensureFresh(id)` (refresh 60 s before expiry; throws `McpAuthRequiredError` from `provider.ts` when the user must sign in again); `store.ts` keeps `tokens` = `{tokens?, savedAt, expired?, origin}` (tokens are only used for that server origin; a record without one reads as signed out), `client` = `{manualClientId?, info?}` (manual client ID replaces DCR) and `verifier` (deleted after sign-in), refuses writes when `safeStorage` encryption is unavailable, and has `authState`/`setManualClientId`/`signOut`/`clearAuthOnOriginChange`. Provider writes are dropped once the connector's revision changes or it is deleted (sign-out and delete bump the revision and cancel an active sign-in), so late refreshes can't restore auth. Testing an edited draft whose server origin changed runs without auth. `safeFetch` refuses a cross-origin 307/308 that carries a body. Each sign-in re-registers via DCR (the loopback port changes). Test auth server `addClient()` pre-registers a manual client. Runner `mcp/client.ts` `runMcp(c)` (set via `setMcpRunner` in `setup/feeds.ts` `setup()`): `ensureFresh`, SDK Client over Streamable HTTP with `safeFetch` and a background provider, `guard.ts` `assertReadOnlyTool` (paged `listTools`, refuses tools without `readOnlyHint: true` before any call), `result.ts` `toolResultData`/`resourceResultData` (plain text is mapped as `{text}`), then the recipe's layout/mapping; 30 s budget, fixed error strings (auth → "Signed out or login expired…"), a view containing a stored token is refused; `authStatus(id)` adds `notRequired` after a tokenless success at the current revision; `testMcpConnector(c)` never rejects; `ensureFresh` proceeds when no tokens are stored. MCP drafts (`connectors/mcpDraft.ts` `McpDraft` = `{id?, kind:'mcp', label, intervalMin?, recipeId, serverUrl, settings?, clientId?}`; `clientId` undefined = keep, null = clear) go through the same `saveConnector`/`testDraft`: the recipe must exist, settings must be declared by it and trimmed within `maxLength`, layout/mapping come from the recipe, a connector can't change kind, a server origin change calls `clearAuthOnOriginChange`, `clientId` goes through `setManualClientId` (rejects when secure storage is unavailable); an unsaved draft is tested under a temporary id with no stored auth, and an auth server then reports "Sign-in required: save, then sign in". Settings IPC (`mcp/ipc.ts`): `listMcpRecipes` (display fields only: id, label, description, defaultServerUrl, layout, source, settings, intervalMin), `mcpSignIn(id)` → `{ok:true}|{error}` (never rejects, `shell.openExternal`), `mcpSignOut(id)` → boolean; `listConnectors` rows for mcp add `auth`, `clientIdSet` and `clientIdHint` (`••••` + last 4), never tokens, verifier, registration or the full client ID (`mcp/leak.test.ts`). Renderer types in `src/preload/index.d.ts` (`ConnectorForSettings` = JSON | MCP, `McpDraft`, `McpRecipeInfo`); the JSON connector form still lists only json rows.
- Connector tabs (M9B client; `mcp:` since M9C): the `tabs` message also carries `connectors: [{id:'json:<id>'|'mcp:<id>',label,layout}]` (client accepts both via `isConnectorId` in `connector/types.ts`) (parsed in `modules/tabs.ts`, absent on older hosts). `client/src/modules/connector/` renders any of four layouts (list, number, keyvalue, grid) from a `ConnectorView` fed by `useFeed(id)`; `connectorModule(d)` builds the module and `App.tsx` appends them to the built-in modules. Types are copied from `src/main/lib/connectors/types.ts`; keep in sync.
- Tab picker (M9A): host `src/main/lib/modules/tabs.ts` stores `tabSettings` = `{order, hidden}` (normalized: unknown ids dropped, missing ids appended, never all hidden), IPC `getTabSettings` (→ `{settings, modules}`) / `setTabSettings`, Settings → Tabs panel. The client sends `{type:'tabs'}` and gets `{type:'tabs', data}`; `data` is `tabsPayload()` (`modules/tabs.ts`) = `{order, hidden, connectors: [{id:'json:<id>', label, layout}]}`, never url/header/mapping, and normalization uses `allModules()` ids; the host rebroadcasts on every change. Client: `contexts/TabsContext.tsx` + `modules/tabs.ts` `visibleIds` (unknown ids ignored; no reply from an older host → every tab); the pager remounts once, on the first reply and only if it differs from the default list (`pagerKeyForFirstReply`), so it starts on the first visible tab; later changes keep the current tab, adjusted during render (`indexAfterChange`). A hidden app's feeds stop polling unless a visible app `dependsOn` it (only Fantasy → Sports); manifests list `feedKeys`; `setup/feeds.ts` `applyTabSettings` starts/stops feeds. `reconcileConnectors()` (subscribed to `onConnectorsChanged`) adds, replaces (new interval; cache dropped if url/header/mapping/layout changed) and removes `json:*` feeds (`unregisterFeed` calls `Feed.dispose()`, which discards in-flight fetches; cache key `feedCache.json:<id>` deleted), re-applies tab settings, rebroadcasts `tabs`. Settings changes (Google, Fantasy, Weather) and a client request still fetch a hidden feed once.
- Feeds (poll + cache + stale): `src/main/lib/feeds/Feed.ts`, built from the module registry in `src/main/lib/setup/feeds.ts`; core (non-app) handlers in `handlers/handlers.ts` (`getHandlers()` is built on first use; manifests import `server.ts` via `time.ts`, so don't read the registry at load time there). Data sources: `lib/google/` (Calendar, Tasks; OAuth in `google/oauth.ts`), `lib/sports/` (ESPN), `lib/fantasy/` (Sleeper, including projections and game status). Each has a `fixtures/` folder.
- Client tabs: `client/src/modules/<id>/` (Weather: `view.ts` helpers, inline SVG `icons.tsx`, shows host labels only); `client/src/App.tsx` builds the pager pages from the registry. Pager: `client/src/components/TabPager/TabPager.tsx`; button keys → tab index in `TabPager/keys.ts` (`keyToIndex(key, current, pageKeys)`). Data: `client/src/hooks/useFeed.ts`. Payload types: `client/src/modules/<id>/types.ts`, re-exported from `client/src/types/Feeds.ts`. Row colors: `client/src/lib/tint.ts` (each sports row takes one team color: the favorite's if exactly one team is a favorite, else the away team's, else none).
- Weather (M8): `src/main/lib/weather/` (`openMeteo.ts` fetch + geocode via the sports `getJson`, `logic.ts` builds `WeatherView` with times in the location's IANA timezone (Intl; fixed UTC offset only as fallback), validates the response (throws `Unexpected Open-Meteo response` so the feed goes stale), `precipLabel` is today's precipitation total in the chosen units, `settings.ts` keys `weatherLocation`/`weatherUnits` (invalid location/units throw; `location: null` clears), `service.ts` feed fetcher + `applyWeatherSettings`). Feed `weather` polls every 15 min (no location → a `kind:'none'` view, not an error); handler `modules/weather/handler.ts`. IPC `searchWeatherLocations`/`getWeatherSettings`/`setWeatherSettings`; a settings change resets the feed cache, refetches and broadcasts. Never log coordinates.
- JSON connectors (M9B): `src/main/lib/connectors/` (`types.ts` model, `LIMITS`; `validate.ts` and `path.ts`/`mapping.ts` build a `ConnectorView` of display-ready strings (list ≤20 rows, grid ≤12 cells, key-value ≤8 pairs, with `more` counts), feed `json:<id>` payload is `FeedPayload<ConnectorView>`, interval 1–1440 min, max 20 connectors; connector fetchers re-read the connector and secret per fetch and never log or show the URL or secret; `fetch.ts` `fetchConnectorJson` (JSON content type only) resolves each hop, checks it with `address.ts` `checkHop` (link-local/reserved refused, NAT64/6to4 and IPv4-mapped unwrapped, http only if every address is local, no https→http), pins the socket to the checked address, 10 s / 1 MB / 3 redirects, secret header only to the original origin; errors never contain the URL or secret; no logging; per-hop resolve/check/pinned socket/error mapping lives in `hop.ts`; `safeFetch.ts` `createSafeFetch()`/`safeFetch` is a WHATWG `fetch` on the same rules for MCP/OAuth (every hop checked, manual redirects, cross-origin drops Authorization/Cookie, streaming body capped at 1 MiB, 10 s total, honours `redirect: 'manual'`); `store.ts`: storage key `connectors` = `Connector[]` (no secrets, re-validated on read), header value in secure storage `connectorSecret.<id>` (`deleteStorageValue` removes it), `saveConnector`/`deleteConnector`/`testDraft`/`onConnectorsChanged`, max 20, ids 8 chars [a-z0-9]; changing a connector's URL origin requires re-entering the header value; `assertNoSecret` fails a feed or test whose mapped view contains the secret; the generic `getStorageValue`/`setStorageValue` IPC refuses both keys (`isProtectedStorageKey`)); Settings IPC `listConnectors`/`saveConnector`/`deleteConnector`/`testConnector` via `connectors/ipc.ts` (responses carry the header name and `headerSet`, never the value; save rejects with a readable message, test never rejects).
- Sleep screen: `client/src/components/Screensaver/`. Long-press helper: `client/src/hooks/useLongPress.ts`.
- Display settings (`sportsTintOpacity`, `calendarTintOpacity`, 0–100, defaults 25/45): `src/main/lib/display.ts`. The client sends `{type:'display'}` and gets `{type:'display', data}`; the host rebroadcasts it when Settings changes a value (IPC `getDisplaySettings`/`setDisplaySettings`). Client side: `client/src/contexts/DisplayContext.tsx` and `client/src/lib/display.ts` (percent → alpha, falls back to the `tint.ts` constants). Sliders: Settings → Client tab.
- Desktop settings UI: `src/renderer/src/pages/Settings/Settings.tsx` (Weather tab: city search via Open-Meteo geocoding through the host, units toggle, clear location; Connectors panel `ConnectorsTab.tsx`: list, add/edit form, Test preview, secret header Set/Replace/Clear; pure form helpers + tests in `connectorForm.ts`). MCP connectors (M9C): the list shows MCP rows (recipe, server host only, auth badge, Sign in/Sign out via `mcpSignIn`/`mcpSignOut`); "Add connector" asks JSON URL or MCP recipe; `McpConnectorForm.tsx` (recipe picker locked on edit, per-recipe settings, optional OAuth client ID with Replace/Clear: `clientId` undefined = keep, null = clear) with pure helpers + tests in `mcpForm.ts`; `ConnectorPreview.tsx` is the shared Test preview.
- Client self-update: on connect the client asks for `version` and sends `update` if it differs from its own, and the host reinstalls it (`handlers/version.ts`, `handlers/update.ts`).
- Device inputs arrive as DOM events: buttons `'1'` (previous tab) and `'2'` (next tab), both wrapping over visible tabs only, `'3'` (jump to Calendar; nothing if Calendar is hidden), `'4'` (does nothing; reserved for sleep-to-clock, roadmap item 4; unverified that it reaches the client), M → `'m'`, Back → `Escape`, dial → `wheel`, dial press → `Enter`.
- Adding a tab: `docs/NEW_APP.md` is the one guide, with a "which path" table (JSON connector, MCP recipe, code-built app module) and a section for each.

## Rules
- Client must run on Chrome 69: no flexbox `gap`, `aspect-ratio` or `:is()`. The legacy Vite plugin handles JS syntax, not new browser APIs.
- The host owns all network calls. The device never sees tokens. Secrets go through `setStorageValue(key, value, true)`.
- The device clock is unreliable: send preformatted times from the host. The `time` message (cron every minute + reply to `{type:'time'}`) is `lib/time.ts` `clockSync()` = `{time, date, now (host epoch ms), offsetMin (minutes east of UTC), hour12 (timeFormat has `h`)}`; a client clock runs from `now` + monotonic elapsed time, never `Date`.
- The Car Thing has no speaker. Alerts on the device are visual; sound has to come from the desktop.
- Tests use committed fixtures and mocked HTTP, never live calls.
- Releases: bump `version` in `package.json` and `client/package.json` (and both lockfiles) to the next `0.0.16-tabs.N` in the milestone PR. After merging, push the tag `v0.0.16-tabs.N` (don't create the release by hand). `build-release.yml` builds it and titles the release `GlanceThing_v0.NN`: one more than the number of existing releases, so titles stay sequential even when a version is never released (tabs.10 is `GlanceThing_v0.08`). The tag is what the update check reads; the title is display only. A release marked as a pre-release is invisible to the in-app update check and the "latest" link.

## Commands
- `npm run gate`: every CI check, printing one line each (plus the tail of any failure). `npm run gate -- fast` skips the two builds; use it between steps.
- Single test file: `npx vitest run <path>`.
- Desktop Settings screenshots (no Electron): `node scripts/preview/settings.mjs <state>`, states in `scripts/preview/settings-states/` (see `scripts/preview/README.md`).
- Add an MCP connector recipe: `Workflow({name:'add-connector', args:{url, goal, toolsList, sample}})` (`.claude/workflows/add-connector.js`; inputs are saved files or pasted JSON, never a live call).
- Recipe helper: `node scripts/mcp-recipe-check.mjs tools|tool|sanitize|id ...` (list read-only tools, check one tool, redact a fixture, check a free recipe id).
- Screenshots of the client at 800×480 with fake data: see `scripts/preview/README.md`. Tab indices start at Weather (0). `VARIANT_<type>=<name>` serves `payloads/<type>.<name>.json` (weather: `metric`, `none`; tabs: `reordered`, `hidden`, `connectors` (adds four connector tabs, indices 6–9), `mcp` (adds the example MCP tab, index 6); no `tabs.json` = old host, every tab). Connector error/stale shot: `env "VARIANT_json-list0001=error" VARIANT_tabs=connectors node scripts/preview/server.mjs &` (hyphenated names need `env`).

## Agent harness (cascading inference)
Applies to every milestone session and every prompt written for one.
- The coordinator (main session) runs on Opus 5.5. It plans the order, delegates, runs the gate itself and owns the PR.
- Each subagent call starts on the cheapest tier that does the job well, and escalates only on evidence:
  - Haiku: read-only lookups (explorer), running commands and reporting output, sanitizing fixtures, screenshots.
  - Sonnet: implementing one planned step (coder), writing recipes, tests and docs.
  - Opus: planning (planner), diff review (reviewer), security-sensitive code (OAuth, secrets, untrusted input) and any escalated call.
- Escalate one tier for that single call when it fails twice on the same step (gate red, acceptance test fails, or its output doesn't match the requested schema). Never escalate a whole phase. Never run planner or reviewer below Opus.
- List every escalation (step, from → to, why) in the PR body.
- Workflow scripts (`.claude/workflows/`) set `model` on every `agent()` call by the same tiers.

## Roadmap (planned, not built)
In this order. Effort is relative to M5/M6.
Items 1–3 are done: **Polish** (M7: one team color per sports row, opacity sliders), **Weather tab** (M8, plus buttons 1/2 = prev/next tab, 3 = Calendar) and **Connector platform** (M9A app modules + tab picker, tabs.8; M9B JSON connectors, tabs.9; M9C MCP connectors + recipes + `add-connector` workflow, tabs.10). New tabs now start from `docs/NEW_APP.md`. Real-service MCP recipes are added later through the workflow, one PR each.

4. **Clock + sleep screen** (medium, merges the old Clock-tab and sleep-clock items): a Clock tab with a timer (alerts are visual only), and a sleep-screen clock with widgets from the existing feeds plus weather, sharing one clock component. Button `'4'` (a no-op in `keys.ts` today) sends the device to sleep on that clock. Button macros, if any, must be long-presses (all four short presses are taken); prefer long-press over double-tap, because double-tap delays every single press by about 300 ms.
5. **Notifications** (medium–large): the host compares each update to the last one against rules (close game, final, fantasy swings, upcoming event), then sends a `notify` message that the client shows over any tab or the sleep screen. Per-type toggles in Settings. Optional desktop notification for sound.
6. **Gmail tab** (medium–large): first try it as an MCP recipe (item 3C); fall back to an app module (item 3A). Needs the restricted `gmail.readonly` scope. Every user has to sign in to Google again, and logins from an OAuth client in test mode expire every 7 days. "Important" means `is:important is:unread`. Build after Notifications.
